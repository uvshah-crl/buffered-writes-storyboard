🪳 CockroachDB Buffered Writes

Understanding How Buffered Writes Optimize Distributed Transactions

What is Buffered Writes?

Buffered Writes is an optimization introduced in CockroachDB v25.2 that temporarily stores transaction writes on the gateway node until commit time, rather than immediately sending them to the storage layer.

🚀

Fewer Round Trips

Batches all writes into one coordinated flush at COMMIT instead of multiple sequential operations

♻️

Redundant Write Elimination

Only the final write for each key is sent to storage, eliminating intermediate updates

🔓

Non-Locking Writes

Can use simpler Put operations instead of conditional CPut operations

📊

Massive Latency Reduction

Multi-region SQL latency reduced from ~20ms to ~2.24ms in benchmarks

v25.2: OFF by default (must enable explicitly) | v26.2+: ON by default | Enable in v25.2: SET kv_transaction_buffered_writes_enabled = true;

How It Works: Technical Deep Dive

❌ Without Buffered Writes (Default in v25.2)

Mental Model: Every SQL write statement is immediately sent to the KV layer while the transaction is in progress. The gateway fires writes eagerly, right when each statement executes.

Example Transaction:

BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 'alice';
UPDATE accounts SET balance = balance + 500 WHERE id = 'bob';
INSERT INTO audit_log VALUES ('transfer', 500, now());
COMMIT;

Key Issues:

  • ⚠️ Sequential network round trips: Each statement blocks on network latency
  • ⚠️ Heavy CPut operations: Conditional puts verify current value before writing
  • ⚠️ Latency multiplier: 3 statements = 3× network cost (21ms + 5ms commit = 26ms)
  • ⚠️ Multi-region penalty: In multi-region, 80ms × 3 = 240ms just for writes!

Problems with this approach:

  • Sequential network hops: Each statement waits for network round trip before next one starts
  • Redundant writes: If you update the same key twice, both updates are sent and replicated
  • Heavier locking: Uses CPut (conditional put) operations which verify current value
  • Latency multiplier: 3 write statements = 3× the network cost

✅ With Buffered Writes

Mental Model: The gateway holds all write operations in local memory (a buffer) and doesn't send anything to the KV layer until COMMIT. During statement execution, the gateway just accumulates what it intends to write.

Same Transaction:

BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 'alice';
UPDATE accounts SET balance = balance + 500 WHERE id = 'bob';
INSERT INTO audit_log VALUES ('transfer', 500, now());
COMMIT;

Single-region: 26ms → 10ms = 2.6× faster

Key Advantages:

  • ✅ Parallel execution: All KV writes happen simultaneously at COMMIT, not sequentially
  • ✅ Simpler Put operations: Uses Put instead of CPut (no conditional check needed)
  • ✅ Latency independence: Adding more statements in transaction doesn't add latency (until COMMIT)
  • ✅ Multi-region wins big: In multi-region, avoid sequential 80ms hops = massive savings
  • ✅ Redundant write elimination: If same key updated twice, only final value is sent to KV layer

Benefits:

  • Parallel execution: All writes sent to their leaseholders at once, not sequentially
  • Eliminates redundant writes: If same key updated twice, only final value sent
  • Simpler operations: Can use Put instead of CPut (no conditional check needed)
  • Dramatic latency reduction: 1 effective round trip vs 4 sequential ones

Side-by-Side Comparison

❌ Without Buffered Writes

Redundant Write Example

BEGIN;
UPDATE inventory SET qty = 10 WHERE id = 'widget';
-- Some logic...
UPDATE inventory SET qty = 7 WHERE id = 'widget';
COMMIT;
1 UPDATE qty = 10 → Network → KV Layer → Raft Replication
2 UPDATE qty = 7 → Network → KV Layer → Raft Replication
3 COMMIT → Network
Cost: 2 full write operations + replication
Waste: qty=10 replicated but never committed

✅ With Buffered Writes

Redundant Write Example

BEGIN;
UPDATE inventory SET qty = 10 WHERE id = 'widget';
-- Some logic...
UPDATE inventory SET qty = 7 WHERE id = 'widget';
COMMIT;
1 UPDATE qty = 10 → Buffer: { widget: 10 }
2 UPDATE qty = 7 → Buffer: { widget: 7 } (overwrite)
3 COMMIT → Flush qty = 7 only
Cost: 1 write operation
Savings: qty=10 never touched the network!

Translation: Same throughput with fewer nodes = lower infrastructure costs

Key Takeaways

✅ Ideal Workloads

  • Multi-statement explicit transactions - Primary target use case
  • Write-heavy workloads - Multiple DML statements per transaction
  • Multi-region deployments - Where network latency is most expensive

⚠️ Limitations & Caveats

  • Version-specific defaults:
    • v25.2: OFF by default - Must be enabled explicitly via session or cluster setting
    • v26.2+: ON by default - Enabled out of the box
  • READ COMMITTED not supported (v25.2) - Only works with SERIALIZABLE isolation (default)
  • Potential retry errors - Some workloads may see increased retries
  • COMMIT gets heavier - More work happens at COMMIT vs during statements
  • Gateway memory usage - Very large transactions may hit limits
  • Observability gap - Limited tracing/profiling for COMMIT-time work

🔧 How to Enable (v25.2)

-- Session-level (recommended for testing) SET kv_transaction_buffered_writes_enabled = true; -- Cluster-level SET CLUSTER SETTING sql.defaults.transaction_buffered_writes.enabled = true;

Important for v25.2: Buffered writes are OFF by default and must be enabled explicitly. In v26.2+, they are ON by default.

Recommendation: Test in staging environment with your actual workload before enabling in production

✨ Advantages

  • "Under-the-covers, no app changes required" - Session/cluster setting flip, no SQL rewrites
  • "Batch your writes, cut your round trips" - Every KV round trip costs latency in distributed systems
  • "Particularly impactful for write-heavy, multi-statement transactions" - Where you'll see the most gain
  • "Significant latency improvements" - Up to 9× reduction in multi-region SQL latency
  • "Lower TCO through improved efficiency" - Same throughput with fewer nodes
